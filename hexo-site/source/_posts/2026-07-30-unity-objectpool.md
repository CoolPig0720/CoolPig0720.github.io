## 一、核心理论

### 1.1 问题起点：Instantiate / Destroy 有多贵

Unity 创建/销毁物体的标准做法是 `Instantiate(prefab)` 和 `Destroy(obj)`。偶尔用没问题，**高频使用**会出大事：

- **创建贵**：Instantiate 要分配内存、克隆组件、初始化物理，是重操作；
- **销毁更阴险**：Destroy 之后那块内存变成"垃圾"，等 **GC（Garbage Collector，垃圾回收器）** 清理。

GC 是 C# 的自动内存管家，但它有个致命脾气：

> **GC 打扫时，整个游戏暂停。**

**类比**：GC 是收垃圾的阿姨，她来的时候全屋人必须原地站住。垃圾攒得越多扫得越久，玩家感受到的"玩着玩着突然一顿"（掉帧卡顿），很多就是 GC 干的。

### 1.2 解药：对象池（Object Pool）

思路：**用完不扔，洗洗再用**。

- 传统做法 = 一次性餐具：用一个扔一个，垃圾山越堆越高；
- 对象池 = 可洗餐具：用完的对象不 Destroy，**关灯收进仓库**（`SetActive(false)`，物体还在内存里，只是隐身+停止活动）；要用时从仓库取出**开灯**（`SetActive(true)`）继续用。

结果：零新垃圾、零新分配，GC 失业，游戏丝滑。

### 1.3 泛型（Generic）`<T>`

**真相：早就在用泛型了**——`Action<float>`、`List<Ball>`、`Queue<T>` 全是泛型。

泛型 = **把类型本身变成参数**。微软写 `List<T>` 时不知道用户要装什么，就用占位符 `T` 代替；使用时填进真实类型。一份代码，万物可装，告别"每种类型抄一份"的复制粘贴地狱。

**类比**：收纳箱的说明书印的是"本箱可装【某物】"，买家自己决定装什么。`T` 就是那个【某物】。

定义泛型类的语法（新语法只有类名后的 `<T>`）：

```csharp
public class ObjectPool<T>
```

类内部所有地方都可以把 `T` 当真实类型用（声明字段、参数、返回值）。

### 1.4 泛型约束 `where T : Component`

矛盾：池子内部要对物体 `SetActive`，可如果使用者填 `ObjectPool<int>` 呢？int 没有 gameObject！

解法：**给收纳箱加"入箱条件"**：

```csharp
public class ObjectPool<T> where T : Component
```

读作"T 必须是 Component 或它的子类"。脚本的继承链是 `Ball → MonoBehaviour → Behaviour → Component`，都能进；int、string 被编译器挡在门外。

**为什么约束到 Component 就够**：`Component` 基类自带 `.gameObject` 属性——Unity 保证每个组件必然依附在一个 GameObject 上，这个属性就是"从组件反向找到宿主"的把手。

### 1.5 Queue&lt;T&gt;（队列）

**先进先出**（FIFO）的集合，像食堂排队。三件套：

| 成员 | 作用 |
| --- | --- |
| `Enqueue(obj)` | 排到队尾（归还入库） |
| `Dequeue()` | 队头出列并返回（取出使用，**空队列调用会抛异常，先查 Count**） |
| `Count` | 当前库存量（注意大写 C！） |

### 1.6 构造函数（Constructor）

> 构造函数 = 对象出生时（new 的瞬间）自动执行的"初始化仪式"。
> 语法特征：**方法名与类名相同、没有返回值类型（连 void 都不写）**。

为什么写了很久 Unity 脚本从没写过构造函数？因为 MonoBehaviour 的出生由引擎接管（用 Awake/Start 代替）。**纯 C# 类**（不继承 MonoBehaviour）才走 `new` + 构造函数的正统路线。ObjectPool 是我第一个"亲手 new 出来的类"。

配套判断：**"全局唯一"用 static class**（如 GameEvents 公告栏）；**"一个模子造多份"用普通类 + new**（红球池、特效池各自持有独立的模板和仓库）。

### 1.7 本课新语法杂货铺

- **`readonly`**：字段在构造函数之后不许再赋值，给字段上保险。适用于"出生时定终身"的字段（模板、仓库）。
- **三元运算符** `条件 ? 值A : 值B`：一行完成"二选一取值"。本课用它把 Get 从 10 行精简到 3 行：`有存货 ? 出队 : 克隆新的`。
- **`this.字段 = 参数`**：参数和字段同名时，`this.` 明确指"我的字段"。这是 this 的第二种用法（第一种是"我这个实例"，见第1课）。
- **`Object.Instantiate`**：纯 C# 类里没有 MonoBehaviour 的便捷方法，Instantiate 要带类名前缀（定义在 UnityEngine.Object 上，写 `GameObject.Instantiate` 也合法）。
- **有返回值的方法**：声明处写返回类型（如 `public T Get()`），方法内用 `return 值;` 交出结果。

### 1.8 局部变量 vs 字段（本课后半场的关键概念）

|  | 局部变量 | 字段（成员变量） |
| --- | --- | --- |
| 声明位置 | 方法大括号内部 | 类的身体里（方法外面） |
| 生存期 | 方法执行完就消失 | 对象活着它就活着 |
| 谁能访问 | 只有那个方法 | 类里所有方法 |

**类比**：局部变量是"临时抄在纸上的名单"，用完就扔；字段是"贴在墙上的班级名册"，一直在那儿。

**缓存改造的本质**：把"每次现场抄名单"（局部变量+每次搜索）升级为"开机登记一次的名册"（字段+Awake 赋值一次）。

## 二、本课最重要的思想课：工具匹配

### 2.1 池子的适用前提

Get 的行为是"从仓库拿**随便一个**，没货就**克隆模板**"，隐含前提：

> **池子里的对象必须是"可互换的克隆体"**——任何一颗子弹都是子弹，拿哪个都一样。

### 2.2 台球是什么

16 颗球是 **16 个独一无二的个体**：白球、7红、7黄、黑8，各有编号、类型、初始位置（Inspector 配置好、场景里摆好）。克隆 template 造出的"新球"没有正确的类型编号，是废球。

**结论：克隆式对象池和"管理 16 颗唯一的球"形状不匹配。** 硬套会扭曲行为，违反第1课铁律"重构不改变行为"。

### 2.3 "进洞的球该销毁吗？"——表现出局 ≠ 内存销毁

我曾提出"逻辑上进洞的红黄球应该销毁"。导师课的结论是一对重要概念的分离：

- **逻辑生命周期**：这颗球"在本局游戏里"结束了（玩家看不见、规则不管）；
- **内存生命周期**：这个 GameObject "在本次运行中"是否还有用。

判断标准只有一条：**它还会回来吗？**

红黄球会回来（重开局全员归位）。Destroy 再重建的代价：Instantiate + 恢复类型/编号/材质/位置——正好是"一次性餐具"反模式，还多了配置出错的风险；隐藏复位则**天然保真**。

> **行业常识：会回来的对象永远不要 Destroy。Destroy 只留给"真的再也不回来"的东西。**

惊人的真相：**本项目"进洞只隐藏、重开局复位"的现有设计，本质就是手写的对象池**——隐藏 = Return，复位 = Get。池化思想早就在用了，只是没起名字。

### 2.4 过度设计（Over-engineering）

顺着"销毁重建"推到底：就算真的销毁，克隆式池还是不匹配（需要"3号红球回来"，池子给的是"template 复制品"）；要修好就得每种球建池、加取出后配置机制……为 16 颗一开始摆好的球造这套机器，就是**为了用工具而改造问题**。

> 第1课：重构不改变行为。第2课姊妹篇：**优化不制造需求。** "手里有锤子，看什么都是钉子"是工程师最常见的翻车姿势。

### 2.5 对症的药：缓存（Cache）

`FindObjectsOfType` 慢在**翻遍场景每个 GameObject 的每个组件**（挨家挨户敲门找 16 个人）。而这 16 个人的名单**永远不变**（球从不销毁/新增）——名单不变的东西，查一次记住即可。

**缓存的成立条件**（永恒代价）：名单在缓存有效期内不会变。若未来有功能动态增删球，缓存必须跟着更新，否则就是"过期名单"。

### 2.6 按调用频率分级处置（性能优化第一课）

全项目 3 处 `FindObjectsOfType` 的"罪行程度"完全不同：

```text
每帧调用（Update内）      → 绝对禁止        （项目中无此情况）
重复性流程（每次重开局）   → 应当缓存        ← GameManager.RestartGame【已改造】
偶发事件（犯规自由球）     → 可以接受        ← CueBallPlacer.BeginPlacing【保留】
编辑器工具（非运行时）     → 无所谓          ← BallRack【保留】
```

> **先看调用频率，再决定值不值得动手。过度优化偶发代码，和过度设计并列浪费。**

### 2.7 读懂旧代码意图再动手：`(true)` 参数的语义

```csharp
FindObjectsOfType<Ball>(true);   // GameManager：带 true = 连隐藏的也算上
FindObjectsOfType<Ball>();       // CueBallPlacer：不带 = 只查激活的
```

两者不是随手写的：GameManager 复位**必须**找到已进袋隐藏的球；CueBallPlacer 做"放白球不许重叠"检测，隐藏的球**不该挡路**。语义不同 → 不能共用一份缓存 → CueBallPlacer 保留原样。

### 2.8 初始化时机的深层意义

同样的开销，Awake 里跑一次可接受、RestartGame 里跑该避免，两层原因：

1. 次数：一次 vs 每局一次；
2. **玩家预期**：玩家对**启动加载**有心理预期（看到 Loading 愿意等），对**交互中的卡顿**零容忍（点"重新开始"时手指在等即时反馈）。

> **同样的开销，挪到玩家"有预期"的时机执行，体验完全不同。** Awake/Start 被称为初始化时机，不只因为"早"，而是"藏在玩家预期之内"。
> 行业变体到处是：加载屏预热资源、过场动画偷偷加载下一关。

## 三、关键语法速查

```csharp
// 泛型类 + 约束
public class ObjectPool<T> where T : Component

// 只读字段
private readonly Queue<T> pool;

// 构造函数（同类名、无返回值）
public ObjectPool(T template, int warmupCount) { ... }

// 三元运算符
T instance = pool.Count > 0 ? pool.Dequeue() : Object.Instantiate(template);

// 关灯/开灯的对象是宿主 GameObject，不是组件本身
instance.gameObject.SetActive(false);

// 数组字段声明（类身体里） + 延迟赋值（Awake里）
private Ball[] allBalls;                    // 声明：类型 + 名字
allBalls = FindObjectsOfType<Ball>(true);   // 赋值：不再写类型！

// foreach 遍历
foreach (Ball ball in allBalls) { ball.ResetBall(); }
```

注意事项：

- 赋值时再写一遍类型（`Ball[] allBalls = ...`）= 声明了一个新的**局部变量**，字段没被赋值——这个陷阱叫**变量遮蔽**；
- `return` 在 void 方法里 = "到此为止"（Awake 单例判定里就有：发现重复实例就 Destroy + return 提前退出，所以缓存登记必须放在 `Instance = this;` **之后**）；
- 格式化快捷键：Qoder/VSCode `Shift+Alt+F`，Visual Studio `Ctrl+K, Ctrl+D`——提交前顺手按一次。

## 四、我踩过的坑（本课真实记录）

### 坑1：`pool.count` 小写 → CS1061

> **报错**：`'Queue<T>' does not contain a definition for 'count'`
> **教训**：C# **大小写敏感**，`count` 和 `Count` 是两个名字。属性是 `Count`。

### 坑2：内外层作用域声明同名变量 → CS0136

if 块里声明了 `T instance`，方法体外层又声明了一个 `T instance`。

> **规则**：外层变量的"领地"覆盖整个方法体（包括里面的 if 块），两个 instance 领地重叠，编译器拒绝。
> **注意**：两个**并排**的 if 块各自声明同名变量没问题（领地不重叠）；**外层和内层**同名才冲突。
> **修复**（选了最优的思路C）：用三元运算符合并"出队或新建"为一条赋值，变量只声明一次，顺带消灭了重复的"开灯+返回"。

### 坑3：`FindObjectsOfType` 丢了 `(true)`，注释与代码打架

字段注释写着"**含已进袋隐藏的球**"，代码却写了不带 `true` 的版本（只查激活的）——**自己的注释出卖了自己**。

> **教训**：Awake 时恰好所有球都激活，结果碰巧一样——但"碰巧成立"不是理由。**把意图写死在代码里，不依赖恰好成立的环境**；写完注释后对照代码检查有没有兑现承诺。

### 坑4：新增代码行顶格没缩进

不影响编译，但破坏可读性，错落的缩进让人误判代码层级。

> **教训**：写完按格式化快捷键（`Shift+Alt+F`）一键对齐，养成提交前格式化的习惯。

### 坑5（概念纠正）：忘 Return ≠ 内存泄漏

思考题⑧推理链正确（忘还 → 池空 → 每次新建 → 池子形同虚设、对象堆积），但结论用词错了。

> **辨析**：泄漏 = "没人用了、却回收不掉"（如第1课 static 事件攥着已销毁对象）。忘还的球是**活着的**（active 在场景里，场景引用着它，GC 本来就不该收）。准确说法：**对象永久流失出池子 + 场景垃圾堆积**——后果同样严重，病理不同。
> **池子的契约**：Get 必须配对 Return（同款纪律：第1课 += 配对 -=）。
