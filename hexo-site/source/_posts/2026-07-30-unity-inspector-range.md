## 一、核心理论

### 1.1 序列化（Serialization）：Inspector 里的值存在哪？

每天在 Inspector 里拖引用、调数值，这些值存在**场景文件（.scene）和预制体文件**里。Unity 把脚本对象的字段值"写进文件保存、读出文件恢复"的机制叫**序列化**。

**类比**：序列化就像给对象**拍证件照存档**——关闭 Unity 时把每个字段的值拍照存进场景文件，下次打开照着照片恢复。**Inspector 就是这套存档系统的编辑界面。**

哪些字段会被拍进照片：

| 写法 | 序列化 | Inspector 可见 |
| --- | --- | --- |
| `public float speed;` | ✓ 默认 | ✓ |
| `private float speed;` | ✗ | ✗ |
| `[SerializeField] private float speed;` | ✓ | ✓ |

### 1.2 特性（Attribute）：贴在代码上的"标签"

> 特性 = 贴在类/字段/方法上的**标签**。它自己不执行任何逻辑，而是等着**别人**（编译器、Unity 引擎、Inspector 绘制系统）来读标签、改变对待方式。

**类比**：快递箱上的"易碎品"贴纸。贴纸本身不保护箱子，是**快递员看到贴纸后**改变了搬运方式。

冷知识：每个特性背后都是一个真实的类（`[Range]` → `RangeAttribute`），方括号是"实例化标签并贴上去"的简写语法。括号里的内容是传给标签的参数。

多个特性可分行叠写（本项目风格），也可挤一行用逗号分隔：`[Header("引用"), Tooltip("...")]`。**保持全项目一致 > 个人偏好**。

### 1.3 特性四件套详解

| 特性 | 类别 | 作用 | 贴在哪 |
| --- | --- | --- | --- |
| `[SerializeField]` | **功能型** | 让 private 字段被序列化 + 面板可见 | 每个需要的字段各贴一次 |
| `[Header("x")]` | 视觉型 | 往下开一个加粗分组 | 每组的**第一个**字段上方 |
| `[Tooltip("x")]` | 视觉型 | 悬停说明，给**调参的人**看 | 需要解释的字段上 |
| `[Range(a,b)]` | 视觉型 | 输入框变滑条 + 钳制手动输入 | 有天然区间的**数值**字段上 |

#### `[SerializeField]`：唯一真正"干活"的

它解决的矛盾——不用它只有两个坏选择：

- `public`：能在面板调，但**任何脚本都能乱改**，破坏封装；
- `private`：封装好了，但**面板看不见，没法调参**。

`[SerializeField] private` 两头兼顾：**对程序员关门，对策划开窗。**

> 镜像特性：`[HideInInspector]` —— public 字段照常序列化，但面板里藏起来。

#### `[Header]`：它不属于那个字段

`[Header]` 贴在字段上，但语义是"**从这里往下开一个新区**"，所以只写在每组第一个字段上方。字段一多（如 CueController 有几十个），没分组的面板就是一片数字沼泽。

#### `[Tooltip]` vs `/// <summary>` XML 注释：分工

|  | 给谁看 | 在哪看 |
| --- | --- | --- |
| `/// <summary>` | **读代码的人**（程序员） | 代码里 / 悬停变量名的智能提示 |
| `[Tooltip]` | **调参的人**（策划、面板前的自己） | Unity Inspector 面板 |

判断标准：这条信息是"**动手配置的人**需要知道的"→ Tooltip；是"**改代码的人**需要知道的"→ XML 注释。重要字段两个都写。

**反面案例**：GameManager 的 `tableSurface` 若只写代码注释，面板前拖引用的人永远看不到"必须和 CueBallPlacer 用同一个台面"，随手拖错就导致出界判定全错。

### 1.4 `[Range(min, max)]` 的两个价值

1. **防手滑**：手动输入也会被钳到区间内——不会出现"想输 0.15 多敲个 0 变 1.5"的事故；
2. **传达设计意图**：滑条两端在告诉所有人"这个参数的合理世界只有这么大"。**Tooltip 是建议，Range 是围栏。**

**破除误解：加了 Range 不是只能拖滑条！**

```plaintext
无 Range：  Off Table Drop   [    0.15    ]
有 Range：  Off Table Drop   ▬▬▬●▬▬▬▬  [ 0.15 ]   ← 右边输入框照样能打字
```

滑条是**多送的**快速试值工具，没有抢走手输能力。唯一的行为改变是超界值被钳制。

**附带好处**：滑块位置本身是信息——看到滑块在偏左 20% 的位置，一眼就知道"当前值在合理区间的靠前段，右边还有大量调参空间"。光看数字 `0.02` 得不到这个信息。

**区别于"标签拖拽"**（按住字段名左右拖动改值）：

|  | 标签拖拽 | Range 滑条 |
| --- | --- | --- |
| 范围 | **无边界**，能拖到几万 | 限定在设计区间内 |
| 传达信息 | 无 | 当前值在区间中的位置 |
| 手滑保护 | 无 | 有 |

### 1.5 特性的能力边界（思考题⑩）

代码里写 `pocketSinkDuration = 99f;` **不会**被 Range 拦住。

> **Range 是给面板前的"手"设的围栏，不是给运行中的"代码"设的围栏。**

因为特性是给 **Inspector 绘制系统**看的标签，而运行时的一行赋值根本不经过 Inspector。**特性只影响编辑器表现，不影响运行时逻辑**——这是无数初学者以为"加了 Range 就万事大吉"的经典盲区。

真要在运行时强制约束，用 `Mathf.Clamp(值, min, max)`（本项目 `Mathf.Clamp01(currentPower)` 就是它的 0~1 版本）。

## 二、本课核心技能：怎么定区间

### 2.1 该加与不该加（思考题⑪）

> **只给"有天然合理区间"的字段加 Range。** 自问：① 有没有"超出某范围必然错误/荒谬"的边界？② min/max 我能不能**说出依据**？

不该加的：

- **非数值字段**（如 `cushionTag` 字符串）；
- **没有对错边界的值**——取决于场景摆放/美术摆位的数值（相机预设位姿、依赖台面尺寸的量），它们的"合理值"由摆位决定，硬加一个拍脑袋的 max 反而是**谎言**，后来人会误以为"超过就不合理"。

**说不出依据的区间，不如不加。**

### 2.2 区间 ≠ 围着当前值画圈（本课最大的坑）

第一版清单我给 `offTableDrop`（当前 0.15）定了 [0.1, 0.2]、`offTableHorizontalMargin`（当前 0.02）定了 [0.01, 0.03]——**都是围着当前值画的小圈**。

反效果：以后想试 0.3 看看效果，滑条不让输，还得回代码改 Range。**Range 从"保护"变成了"绊脚石"。**

> **正确含义：min/max 不是"我现在觉得好用的范围"，而是"超出此界必然荒谬"的边界。区间内要留足调参探索空间，当前值通常应落在区间靠前段。**

### 2.3 "荒谬检验法"：依据从哪来

对每个端点问：**这个值取到多少会变得荒谬？荒谬在哪？**

依据的三个来源：

1. **物理量锚点**：球半径 0.028m、直径 0.057m —— 阈值小于一个球的尺度必然是误判；
2. **字段注释**：`offTableHorizontalMargin` 的注释明写"0=正好台面边缘" → min=0 的依据现成的；`sweepCaptureScale` 注释写"**>1** 补偿偏心入袋" → min=1 的依据现成的；
3. **功能失效点**：捕获系数太大 → 会把台面上正常滚动的球误吸进袋 → max 的依据。

> **区间的依据从字段语义、注释和物理量里读出来，不是拍脑袋。**

## 三、我踩过的坑

### 坑1：以为 Range 会牺牲手输精度 → 拒绝使用

以为加了 Range 只能拖滑条，精度不如手输，所以不想用。

> **纠正**：Range 是"滑条 + 输入框"并存，手输能力完全保留。
> **教训**：对一个功能的抗拒，先确认自己对它的理解是否准确——**基于误解做的技术决策，是最隐蔽的浪费**。

### 坑2：把"调好的值域"当成"合理区间"

见 2.2。区间太紧 = 未来的自己被绊住。

### 坑3（最重要）：放弃自己有依据的推理，去迁就导师一句没依据的话

第二版我按球半径推出 `offTableHorizontalMargin` max ≈ 0.03（"0.03 已大于半径 0.028，球超出一个半径就会掉了"）——**这个物理推理是正确的**。

导师说"真正的 max 比 0.03 大得多"（**导师没算量级，这句是错的**），我就改成了 **0.3**（= 30cm，超过台宽四分之一，球飘出台外 30cm 还不判出界 → 检测等于永不生效，比 0.03 更荒谬）。

而我当时的原话是："我一开始是这么想的，**但是你说还不够，那我改成 0.3**"。

> **教训：依据 > 权威。** 导师的话也必须接受"荒谬检验法"的检验。正确反应是**反问**："我按球半径算的，0.03 已超过一个半径，你说还不够——依据是什么？"——一问对方就得承认算错。
> **附带认知**：这也是"每个区间都必须写依据"的深层价值——**依据是可被审查的，数字不是**。只交数字，错误就会被埋进代码，谁也发现不了。

最终定稿 max = 0.1（≈3.5 个球半径）：比调参舒适区宽数倍，又不到"永不判出界"的荒谬区。

## 四、最终成果

| 字段 | 区间 | 依据 |
| --- | --- | --- |
| `Ball.offTableDrop`（当前 0.15） | [0.05, 0.5] | min：小于一个球直径（0.057m）的下坠必然是误判；max：留足探索空间，再大则永远判不出界 |
| `Ball.offTableHorizontalMargin`（当前 0.02） | [0, 0.1] | min=0：注释明定"0=正好台面边缘"，负值意味判定线跑进台面内部；max≈3.5 个球半径，超此距离球必然已完全离台 |
| `PocketDetector.sweepCaptureScale`（当前 1.25） | [1, 2] | min=1：注释要求 >1，等大于触发器是下界；max=2：捕获半径两倍于袋口，再大会误吸台面上正常滚动的球 |

未加 Range 的字段（有意为之）：`cushionTag`（字符串）、`pocketSinkDuration` / `pocketSinkDepth`（本轮未纳入，纯视觉动画参数）。

**项目规矩确立**：特性顺序统一为 `[Tooltip]` → `[Range]` → `[SerializeField]`，三处一致。

**待办（可选）**：把三条依据补进 Tooltip——面板上调参的人正需要这个信息。
